# RootHide 1.15.4 新账号复测：第二次密码确认仍存在

本次续测使用用户另提供的测试账号。验收条件继续要求：改机保持启用，一次密码提交后完成必要双重认证，App Store 登录成功且重开保持，并由后台设备详情核对本轮机型、序列号和系统版本。第二次密码确认不算通过。

## 结论

**本轮未通过，故障仍存在，尚未修复。** 1.15.4 前一轮在另一账号上完成登录、重开保持和后台三项字段匹配，是该轮已观察到的事实；本次结果说明它不能作为所有账号及日常操作均正常的保证。保留原始 `v1.15.4` 标签、源码提交和两份 DEB，不用失败对照覆盖这些产物。

设置顶部已观察到“登录 iPhone”，未登录 iCloud 主账号。每个有效登录对照都先在 App Store 确认未登录状态。该现象不能证明所有系统账户缓存均已清除，也没有证据将失败归结为旧 iCloud 账号。

## DPP 实际补充分析

参考仍为用户给出的 [1024.zone 软件源](http://1024.zone.id) 内 DPP RootHide 2.1。该 daemon SHA-256 为 `c7daaaef184146348e91ff3186d439464e04c5c0bbf49d443171197bda5e6a59`。

本轮实际用 REA / Ghidra 对 daemon 执行 `/usr/bin/killall` 字符串跟踪，定位到 `0x100012e40`，反编译显示它遍历给定进程名单，拼接 RootHide 根目录下的 killall 路径，并传入 `-9` 和进程名。继续追踪调用者 `0x10000bf2c`，得到固定六项：SpringBoard、lockdownd、akd、accountsd、itunescloudd、identityservicesd。

这证明样本中存在该刷新例程及名单；本轮尚未将完整上游调用关联到 DPP 界面某个动作，不能声称已经动态观察到 DPP 每次改机都执行它。MKS 的六进程刷新对照也不等于执行了这一完整名单。后续须继续追踪具体触发路径，并比较认证实际读取数据，不以复制一个过滤列表代替功能验证。

## 第三方组件与回滚

手机中的 appdelegate.dylib 归属 `com.zjx.ioscontrol`，过滤声明为 `com.apple.UIKit`。pccontrol 的声明目标是 SpringBoard，ssdd / ttre 的声明目标是列出的游戏应用。这些只是已安装过滤声明，不冒充运行态模块加载或因果证据。

临时修改了 `mks.plist` 与 `appdelegate.plist` 两个过滤文件；二进制、账号数据和 Keychain 未删除。已在独立副本测试恢复原文件 SHA-256，再在手机恢复两个原文件并刷新目标进程。最终继续保持 1.15.4，原过滤与插件配置已回到实验前状态，本轮随机参数仍启用，App Store 已核对为未登录。

原始截图、账号相关画面、配置、SHA-256、事件 JSON、REA 输出与可执行回滚脚本均保存在本地忽略目录，不上传账号、密码、完整设备身份或会话数据。
